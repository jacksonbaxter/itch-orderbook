ITCH order book replay in WebAssembly

One symbol's trading day from Nasdaq's TotalView-ITCH 5.0 sample, replayed message by message through the project's own L3 book, compiled to WebAssembly with Emscripten. The engine is the same C++ as the native build: FastBook, the paged index with flat levels, the arm the project ships.

Set up the demo

From the repository's root, with Emscripten and the release build available:

python3 scripts/fetch_data.py --day 12302019
cmake --preset release && cmake --build --preset release --target itch_extract
python3 scripts/demo.py extract --day data/12302019.NASDAQ_ITCH50 --symbol AAPL
python3 scripts/demo.py build
python3 scripts/demo.py serve

Then open the address demo.py serve prints. The extract is Nasdaq's data: it lives in docs/local/, which git ignores, and is never committed or deployed. Opening this file straight from disk does not work, because browsers block module and WebAssembly loads from file://.

Why this page cannot show low latency

WebAssembly cannot show true low latency, and this page does not try:

  • The browser's clock is clamped. Chrome rounds performance.now() to 100 µs, or to 5 µs on a cross-origin isolated page; Firefox and Safari to 1 ms, or 20 µs. A book message takes well under a microsecond, so one message is far below what the clock can see.
  • This browser's clock steps by an amount not yet measured, and this page has not checked whether it is cross-origin isolated.
  • WebAssembly has no clock, no cycle counter and no way to pin a thread: there is no instruction for any of them. The engine cannot time itself, so the page times whole calls into it from JavaScript, and the JIT, the garbage collector and the rest of the browser run beside it on cores the page cannot choose.
  • So messages per second come from batches only: the time of a batch of many messages, divided by their count. Per-message latency cannot be measured here at all, and the page shows none. The percentiles above come from the native build on a pinned core.
  • Memory is bounded. wasm32 addresses at most 4 GB, and Emscripten's default maximum is 2 GB. This engine has a fixed 1 GiB that never grows, and the book at the capacity the project ships holds about 663 MiB of it, so the page replays one symbol's extract and never the 7.7 GiB day.

GitHub Pages cannot set the headers that isolate a page, so a hosted copy would get Chrome's coarser clock. This page is not deployed anywhere: the extract it replays is Nasdaq's data.
