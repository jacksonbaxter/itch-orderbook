## What a reviewer is

A reviewer here is a subagent session that did not write the code it read. It was given the code, not the author's conclusions, and asked for anything it would block a merge for: for each problem the file and line, why it is wrong, how to show it fails, and a fix. A finding is BLOCK (the reviewer would block the merge), FIX (should be fixed, would not block) or NOTE (worth knowing). Every outcome below was checked in the tree at the commit above, not taken from the fixer's report: each commit named is in the history, each test and fault named is in the tree, and each docs/NOTES.md section named is there. `scripts/review_report.py check` checks them again each time it runs.

Fixed: changed, with the commit that changed it, and the tests and faults that hold the fix where there are any. Known limit: left as it is, with the reason in the docs/NOTES.md section named. No change needed: checked, and the code was right or the point was taken as it stands. Left for the owner: the owner decides. Partly: part of it is still to do. Open: not done yet.

What the script checks, and what it cannot. `scripts/review_report.py` refuses a finding fixed with no commit, unless it says in words why there is none, and a known limit with no docs/NOTES.md section; and `check` refuses any commit, test, fault or section named that is not in the tree. It cannot tell whether the evidence named is the right evidence: that the commit fixed that finding, that the test or fault holds it, or that the section gives its reason. The record's author checked that for every finding, against the tree at the commits above, and two later reviewers checked them again: r15 a sample of them, and r16 every outcome of r15's findings.
