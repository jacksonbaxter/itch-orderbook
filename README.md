# itch-orderbook

A feed handler and full-depth (L3) order book for Nasdaq TotalView-ITCH 5.0 in C++23, with an event-driven backtester, a market maker, a lock-free SPSC ring and a browser demo built on it. It is built to be measured on real data: every target in [BENCHMARKS.md](BENCHMARKS.md) has a published source, and every measured figure on this page and in [RESULTS.md](RESULTS.md) comes from the file in [results/](results/) that its line cites, the tables generated from them.

The fast book is compared with a deliberately simple reference book after every message, and over 10 full trading sessions, 3,081,392,329 messages, the two never diverged ([results/oracle_sessions.md](results/oracle_sessions.md)). A test counts every call to `operator new`, and the book makes none after warm-up.

Speed is measured on `debian`, an AMD Ryzen Embedded V1605B (Zen 1, 4 cores and 8 threads, turbo on), with each thread pinned to its own core. There the `paged-flat` book rebuilds every symbol's L3 book at 5.15 M messages/s with the day in memory, against T-BOOK-1's bar of 16.4 M set on a Ryzen 7 9700X: a miss by 11.25 M. Turbo was on, so the clock was not fixed: one reading of core 4 before the run gave 3593024 kHz ([results/bench_book_paged-flat_ram_debian_12302019.md](results/bench_book_paged-flat_ram_debian_12302019.md)). The parser alone, on the same host and day, walks the frames at 298,983,253 messages/s, 9.180 GB/s, against T-PARSE-1's bar of 709 M; its strict decode of every field of every message runs at 117,739,800 messages/s, above T-PARSE-3's bar of 93.9 M, which is set on another day, 10302019, where no run was timed ([results/parse_rate_debian_12302019.md](results/parse_rate_debian_12302019.md)).

On the Mac, an Apple M4 Max that cannot pin a thread, the same design runs at 21.87 M messages/s ([results/bench_book_paged-flat_ram_mac_12302019.md](results/bench_book_paged-flat_ram_mac_12302019.md)). That is a macOS figure against a bar set on x86 Linux, so it is neither a pass nor a fail. Most bars were set on desktop x86 parts, and on `debian` the book misses most of them: [RESULTS.md](RESULTS.md) gives every gap, and [docs/NOTES.md](docs/NOTES.md) what was found about each; for most the cause is not established.

[WRITEUP.md](WRITEUP.md) walks through the design trade-offs with their numbers: data layout, memory, branches, what did not work, and every target missed or not measured.

## What is built

- A parser for the framed feed, with no abort reachable from wire content, and SIMD kernels for NEON, SSSE3, AVX2, AVX-512 VBMI and WebAssembly SIMD128, each compared with scalar by the tests on a CPU that has it. On both hosts the parser's default stays scalar.
- `FastBook` in four arms, a hash or paged order index with linked or flat levels, measured against a `std::map` book on a fresh heap or one aged as it goes. The default arm is the paged index with flat levels, the fastest on both hosts.
- An oracle that compares the fast book with a slow reference book after every message of a real day, with the proof that the state it skips cannot have diverged in [docs/NOTES.md](docs/NOTES.md), and trade-print checks against SEC MIDAS and Nasdaq CrossStats. T-TRADE-3, each symbol's volume against MIDAS, fails on four of the ten sessions, and T-TRADE-5, every `E` in normal trading at the best price, on two; [RESULTS.md](RESULTS.md) lists each failure. T-INV-2, the strict never-crossed invariant, fails on real data and stays failing; [RESULTS.md](RESULTS.md) says why.
- A benchmark harness that measures any book design, records its host, refuses to publish a run it cannot stand behind, and reads hardware counters on Linux. Counters and flamegraphs are from `debian`, where T-PERF-1 and T-PERF-2 fail.
- An event-driven backtester: simulated orders queued among the real ones by their order references, with latencies, a share ledger and per-fill fees, checked on 48 hand-worked scenarios and for lookahead. It has no market impact, by construction. On `debian` T-BT-1 is met and T-BT-3 is missed.
- An Avellaneda-Stoikov market maker on the backtester, calibrated on 10302019 and reported on 12302019, its PnL split into spread capture, adverse selection and inventory ([results/mm_pnl_12302019.md](results/mm_pnl_12302019.md)). No edge is claimed.
- T-MM-2, the replication of the Avellaneda-Stoikov paper's tables, fails: one of three average spreads, at γ = 1, is 3.03 at two decimals against the paper's 3.02 ([results/mm_as_tables.md](results/mm_as_tables.md)).
- An SPSC ring, compared with other queues, ablated one technique at a time, and run between a parser thread and a book thread. On `debian` T-SPSC-1 and T-SPSC-2 are missed and T-SPSC-3 is met.
- A pool allocator for the book's nodes, and T-ARENA-1's allocator arms. On `debian` the arms ran with the pools on base pages ([results/alloc_arms_base_debian_12302019.md](results/alloc_arms_base_debian_12302019.md)) and on transparent huge pages ([results/alloc_arms_transparent_debian_12302019.md](results/alloc_arms_transparent_debian_12302019.md)). T-ARENA-1 has no bar. Every arm's book agrees with the fast book, and the pool arms allocate nothing over the day, but the fault check fails in both files: a pool arm must take no page fault in a timed pass, and `pool-index`, `pool-pointer` and `pool-fifo` take 136, 200 and 146 on base pages and 4, 1 and 0 on transparent ones, which [docs/NOTES.md](docs/NOTES.md) traces to the kernel moving pages under the running book. The arm on explicit huge pages has not run: `debian` has none reserved, a root step left to the user.
- A UDP replay of the feed for T-URING-1 and T-URING-2: MoldUDP64 framing, a paced sender, `bench_udp`, and nine receive modes, S1 to S4 on sockets and U1 to U5 on io_uring. S1 builds everywhere, S2 to S4 on Linux, CI included, and U1 to U5 where liburing is, which is `debian` alone; there every mode is built and tested and has been timed over loopback, a syscall-and-copy benchmark on one host and not a network one ([results/udp_bisect_debian_12302019.md](results/udp_bisect_debian_12302019.md)). T-URING-1 has no bar: S4, which spins on `recvmmsg`, carries the most with no loss, 2,830,848 messages/s; U2 and S3, the headline pair, tie at 2,735,896; U4 and U5 come last, held down by their buffer rings running dry. T-URING-2 is met: S4 is lossless at 2,547,190 messages/s, Nasdaq's 1 ms peak rate, in 10 runs of 10. Every mode is also lossless on a window of the day replayed by its own timestamps, at its own pace and sped up to Nasdaq's peaks.
  At 72 bytes a datagram, the smallest that carries every message of the day, the sender is the limit: no mode lost a datagram, every mode but U4 ran until the sender fell behind, at 187,539 (S2) to 232,897 (S4) messages/s, and U4 stopped at 220,621 when its buffer ring ran dry ([results/udp_bisect_72b_debian_12302019.md](results/udp_bisect_72b_debian_12302019.md)).
- A browser demo in `docs/`: the same `FastBook` compiled to WebAssembly, replaying one symbol's extract that a script cuts locally, and T-WASM-1's harness, which times it against native on the Mac in Chrome for Testing.
- Fuzz targets, sanitizer builds, and a fault matrix that shows each check failing on a planted bug.

The GitHub Actions workflow in `.github/workflows/ci.yml` builds the release preset and runs every unit test on x86-64 Linux with GCC and Clang, arm64 Linux with GCC and arm64 macOS with Clang, and builds the parser and the demo's engine with Emscripten. The sanitizers, clang-tidy and the fault matrix run in `scripts/check.sh`, not in CI. [docs/NOTES.md](docs/NOTES.md) says what the first runs on GitHub found.

## Build and test

You need CMake, Ninja, Python 3 and a C++23 compiler, taken from `CC` and `CXX`. Clang and GCC 14 both build it.

```sh
cmake --preset release
cmake --build --preset release
ctest --preset release
```

The presets are `release`, `asan-ubsan`, `tsan`, `fuzz`, `tidy` and `wasm`. `wasm` needs `EMSDK` set. `fuzz` needs a Clang with libFuzzer.

Third-party code comes through CMake FetchContent, each pinned by SHA-256 in `cmake/ItchDependencies.cmake`, into `build/_downloads`. `ITCH_MIMALLOC`, which fetches mimalloc for the node book's mimalloc arm (T-ARENA-1), is on in the `release` and `tidy` presets and off in the others. Two more are off unless you turn them on:

```sh
cmake --preset release -DITCH_COMPARISON_QUEUES=ON       # the queues T-SPSC-1 compares against
cmake --preset release -DITCH_LIBURING_ROOT=<prefix>     # a liburing build, Linux only
```

## Fetch the data

The ITCH days and reference files are not in this repo. They go to `data/`, which is gitignored.

```sh
python3 scripts/fetch_data.py --day 12302019     # fetch one day and verify it
python3 scripts/fetch_data.py --ref all          # CrossStats and MIDAS
scripts/check_real_day.sh                        # the checks that need a real day
scripts/check_real_day.sh --arms all             # the same, on every arm of the fast book
```

## Run the demo

`docs/` holds a static page that replays one symbol's extract on the same `FastBook` as the native build, compiled with `em++ -O3 -msimd128` into a fixed 1 GiB memory, and animates its depth and trades. The extract and the engine are made locally into `docs/local/`, which is gitignored, so no market data is committed. The page is not deployed anywhere. <!-- figures: not measured -->

```sh
cmake --preset release && cmake --build --preset release --target itch_extract
python3 scripts/demo.py extract --day data/12302019.NASDAQ_ITCH50 --symbol AAPL
python3 scripts/demo.py build      # needs EMSDK set
python3 scripts/demo.py serve      # then open http://127.0.0.1:8000/
```

The server sends the cross-origin isolation headers, so the browser's clock is clamped to 5 µs in Chrome rather than 100 µs, and `file://` cannot load the engine. The page shows messages/sec from whole batches only and no per-message latency, and says why. <!-- figures: not measured -->

## Check everything

```sh
scripts/check.sh               # every stage, one at a time
scripts/check.sh --quick       # the stages a change should pass before a commit
scripts/check.sh --list        # the stages
scripts/check.sh --only NAME   # one stage
```

It reads nothing from `data/`. Each stage's log is in `build/check-logs/`.
